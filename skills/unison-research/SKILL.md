# Resolve uncertainty with primary evidence

Start with the installed UCM version and exact package or feature in question.
Use the [source catalog](../../research/sources.md) to locate relevant documentation.
Read [talk notes](references/talks.md) for historical material and transcript provenance.
Use [community routing](references/community.md) when preparing a bug report or a question that local evidence cannot resolve.

## Verify a claim before making it an instruction

1. Inspect local help, MCP schemas, and installed definitions for the current project.
2. Consult official documentation and release notes matching the installed version.
3. For a library, inspect its README and exact release through Share/UCM.
4. For rationale, read a maintainer's article or conference/interview transcript.
5. Reproduce syntax or behavior in a small disposable transcript when practical.
6. Save a concise derived note with source URL, retrieval date, version, and verification status.

Use precise searches, such as `site:unison-lang.org abilities handler` or an exact error message with `unisonweb/unison`.
Disambiguate the programming language from the file synchronizer, labor union, and unrelated agent projects.
When a page returns only a JavaScript shell, use UCM's Share tools or a rendered browser; record the limitation if unavailable.

## Use video transcripts without inventing evidence

Prefer the publisher's transcript or captions, then the speaker's companion article or slides.
Record the title, speaker, source URL, publication date when known, and whether text came from captions, a transcript, or a summary.
Preserve actual timestamps when provided. Do not generate plausible timestamps or call a video description a transcript.
Cross-check API names and syntax against current definitions: transcription can corrupt punctuation and identifiers.

Keep derived lessons and brief excerpts; avoid republishing full third-party transcripts.
Label unverified leads explicitly. A roadmap or historical prototype is not a shipped capability.

## Update the smallest useful reference

Revise the relevant specialist and add or rerun a meaningful example for behavior changes.
Run the repository's structural validator and examples.
Record the verification date and result in the source catalog or validation report.
Do not add speculative rules to every skill because one example failed.
